# Terra_Food 开屏与移动端性能优化实施报告

## 1. 结论

本轮已完成开屏依赖拆分、路由分包、登录预热移除、想吃匹配限界、图片派生、轻量分页、公共发现缓存、地图聚合、请求计时和独立性能环境建设。

在小主机的独立 M 数据集（10,000 道菜）、移动视口 390×844、CPU 4 倍降速、下行 1.6 Mbps、上行 750 Kbps、RTT 150 ms 条件下：

| 指标 | 基线中位数 | 优化后中位数 | 变化 |
|---|---:|---:|---:|
| 搜索可操作 | 2,874 ms | 2,122 ms | -26.2% |
| 首批菜品可见 | 3,712 ms | 2,301 ms | -38.0% |
| 桌面首批菜品可见 | 702 ms | 259 ms | -63.1% |

移动端首批菜品可见达到不超过 3 秒的本轮实验室目标。身份、标签各延迟 5 秒且瓦片失败时，公共目录仍在 224 ms 可用；身份确定前私人请求数为 0，开屏音频请求数为 0。

这些结果来自合成数据和容器级内存限制。小主机不是用户真实环境，也没有生产数据、生产磁盘争用、真实图片分布和真实手机网络，因此尚不能证明线上卡顿全部消除。上线前仍需用脱敏规模统计校准数据集，上线后按真实用户设备记录关键阶段。

## 2. 实施范围

### 2.1 开屏关键路径

- 公共路由直接进入，不再等待会话恢复。受保护路由仍等待身份确认，服务端权限校验保持不变。
- 身份恢复、成就通知、地区、标签、目录和地图分别加载。个人区域只在身份确定后请求。
- 路由全部改为动态导入；上传、编辑、分享、印记和 Agent 等非首屏组件按需加载。
- 主入口包从 554.62 KiB（gzip 180.22 KiB）降至 277.73 KiB（gzip 101.24 KiB）。首页成为独立 175.38 KiB（gzip 52.03 KiB）分包。
- 移除远程 Google Fonts 首屏依赖，改为系统中文衬线字体栈。
- 音频使用 `preload="none"`，只有用户播放时才加载。
- 首页不再主动申请定位权限；地图仍自动启动，默认全国视野。
- HTML 内置轻量启动占位、无脚本提示和分包失败后的手动刷新入口，没有最低展示时长和无限重试。

### 2.2 请求竞争和失败隔离

- 目录和地图均向 HTTP 层传递真实 `AbortSignal`，同时使用请求序号阻止过期响应回填。
- 搜索、回车、筛选、URL 前进后退共用一份查询状态。
- 新查询取消旧查询；组件卸载时取消请求和定时器；取消不显示为业务错误。
- 地图移动结束后防抖 250 ms。
- 目录、地区、标签和地图分别显示错误并支持局部恢复。已有内容在刷新失败时保留。
- URL 中已有标签 ID 时，标签名称列表尚未返回也不会丢失筛选条件。

### 2.3 登录与想吃

- 登录响应不再同步执行地图预热或想吃匹配，也没有用无界后台任务替代。
- 删除旧全量 `matchingCatalog` 服务和 Mapper 查询，防止后续代码重新调用全库完整对象路径。
- 想吃区域按需分页加载。空列表立即返回，单测验证不会查询菜品候选。
- 已关联条目按 ID 检查目标；自由文本先从数据库取得最多 200 个可见候选，再计算 Top 3。
- 每个条目的规范化文本和词元只计算一次；候选不足时按实际数量返回。
- 小型建议结果按用户、条目内容版本和公共数据版本缓存 5 分钟。

### 2.4 图片交付

- 原图和原 `imageUrl` 保持兼容；新增图片资源记录、尺寸、状态、处理版本、错误类别和 320/640/1280 三档派生地址。
- 上传先原子保存原图，再读取尺寸和登记资源，不等待派生图完成。
- 24 MP 以上图片保留原图并标记不派生；不透明图片输出 JPEG，透明图片输出 PNG；小图不放大。
- 派生处理单并发、有界取一条、持久化状态；临时文件完成后原子替换。失败保留原图并清理不完整派生文件。
- 首次 GET 不执行转码。
- 菜品卡片使用固定比例、`srcset/sizes`、懒加载和异步解码；派生未完成时回退原图，失败只尝试一次备用地址。
- 新增人工补图命令，默认 dry-run、每批 100、支持游标续跑和失败重试；仅扫描配置上传目录内的 JPG/JPEG/PNG/WebP。
- 补图命令在正常 Servlet 上下文中使用随机端口启动，完全就绪后有序关闭。小主机 dry-run 返回码为 0，统计为 `examined=1 queued=0 skipped=1 failed=0`。
- 孤立图片清理识别原图与派生关系，避免删除仍被引用的派生资源。

### 2.5 查询、分页和缓存

- 新增目录卡片轻量投影；旧目录响应默认保持，新前端显式请求 `compact=true`。
- 评论、收藏、想吃补齐分页接口，默认 20、最大 50；首页收藏请求 10 条。
- 个人中心按当前区域请求收藏和想吃，进入页面不再同时装载这两组完整列表。
- 目录、计数、地图使用相同的规范化筛选参数；无关键词热度浏览使用专门索引路径。
- 公共目录和计数缓存 60 秒，地图缓存 30 秒，想吃建议缓存 300 秒。
- 缓存键规范化关键词、标签顺序、分页、排序和边界；公共数据修改后清理发现缓存。
- `sync=true` 合并同 JVM 内相同键的并发回源；Redis 故障时可回源数据库。
- 私人正文和会话未进入公共发现缓存。
- V21 增加经过查询计划检查的热度、地区、创建时间、收藏、评论及图片引用索引。

M 数据集查询计划显示：无筛选热度目录使用 `idx_food_review_heat_id`；关键词仍使用状态索引后执行 `INSTR`；地图范围聚合仍需要临时表。后两项解释了 L 数据集冷查询的增长风险。

### 2.6 地图

- 新增 `GET /api/foods/map-clusters` 和聚合成员分页接口；旧 markers/map-results 保留。
- 服务端按当前视口、缩放和统一筛选对象使用 Web Mercator 网格聚合。
- 响应包含数据版本、视口匹配数、实际聚合级别和点/聚合列表。
- 单次最多 300 项；超出时降低精度并重新聚合，不把前 500 条当作总数据。
- 稳定网格 ID 支持前端增量添加、更新和移除，避免每次平移清空全部图层。
- 聚合点击放大；同坐标无法继续展开时按 20 条分页读取成员。
- 弹窗内容点击时创建；移动端取消地图瓦片颜色滤镜并减轻大面积模糊。
- 地图错误显示在地图内部，不覆盖搜索和目录。

### 2.7 可观察性与代理示例

- 前端记录应用挂载、首页挂载、目录完成、身份完成和地图完成等本地性能标记；测试读取，不自动上传用户数据。
- 后端为每个请求记录请求 ID、路由模板、状态和耗时，并返回 `X-Request-ID`。
- 日志不记录完整搜索词、Cookie、验证码、私人正文或完整请求体。
- Nginx 示例启用 gzip、版本化静态资源一年 immutable 缓存、HTML no-cache、上传资源缓存、6 MiB 请求体预算和上游计时访问日志。
- 私人 API 保持 Spring Security 的 no-store 响应，不统一代理缓存。

## 3. 接口与迁移兼容

| 项目 | 新行为 | 兼容策略 |
|---|---|---|
| 登录 | 移除同步业务预热 | 响应字段不变 |
| 目录 | `compact=true` 返回轻量卡片 | 默认仍为原响应 |
| 地图 | 新增聚合与成员分页 | 旧地图接口保留 |
| 图片上传 | 可返回资源 ID、尺寸、状态和派生图 | 原 `url` 保留 |
| 收藏/想吃/评论 | 新增分页响应 | 旧列表接口保留且不触发想吃全库扫描 |
| 数据库 | V21 新增 `image_asset` 和性能索引 | 原图和原字段保留；不修改旧迁移 |

推荐兼容发布顺序为后端、前端、历史图片补处理。前端回滚后仍可读取旧字段；后端回滚前必须在恢复副本中验证旧版本面对 V21 迁移记录的行为。

## 4. 验证环境

- 主机：小主机，仅作为隔离测试执行器和未来服务器候选。
- Compose 项目：`terrafood-perf-20260910`，端口只绑定 `127.0.0.1:18280`。
- 独立 MySQL、Redis、上传卷和网络；未连接测试部署或生产数据库。
- 被测服务上限：后端 768 MiB、MySQL 768 MiB、Redis 128 MiB、Nginx 64 MiB，合计 1,728 MiB。
- JVM：堆 384 MiB、SerialGC；Hikari 最大 8；MySQL buffer pool 256 MiB、最大连接 30。
- 浏览器和压力执行器在上述 1,728 MiB 预算外。
- 数据集：S=1,000、M=10,000、L=50,000；包含密集点、同坐标、长文字和不同热度。它们是合成数据。
- 移动浏览器：390×844、CPU 4 倍降速、1.6 Mbps/750 Kbps、RTT 150 ms；五个独立冷上下文。

Compose 的独立容器上限不能完整模拟 2 GB 虚拟机的内核、页缓存、磁盘、swap 和其他进程争用。因此报告使用“2 GB 约束合成验证”，不使用“等同线上”。

## 5. 验证结果

### 5.1 构建、迁移和功能

- 后端测试：95 项，0 失败，0 错误，1 项既有跳过。
- 前端生产构建通过，路由分包产物生成。
- MySQL 8.4 从 V1 到 V21 全部迁移并启动成功。
- 独立环境：登录 200、图片上传 201、目录 200、地图聚合 200。
- 透明 PNG 上传后资源状态为 READY，三档派生文件均存在。
- 请求响应包含 `X-Request-ID`。
- 补图 dry-run 完成并以 0 退出。

### 5.2 M 数据集服务端

最终实现的 p95（毫秒）：

| 场景 | 并发 1 | 并发 5 | 并发 10 | 并发 20 | 目标 |
|---|---:|---:|---:|---:|---:|
| 无关键词目录 | 199 | 137 | 193 | 363 | 500 |
| 关键词目录 | 422 | 76 | 119 | 222 | 800 |
| 地图聚合 | 271 | 79 | 107 | 202 | 800 |

所有请求均无失败。并发 5–20 的同键结果包含缓存和回源合并收益，不能解释为每次都执行数据库查询。冷请求值应参考并发 1 和 L 数据集风险。

基线 M 数据集中，无关键词目录在并发 20 时 p95 为 2,173 ms，旧 markers 为 1,348 ms；基线关键词在并发 5 时达到 4,185 ms 后按压力停止继续升档。

### 5.3 L 数据集增长调查

- 无关键词目录在并发 20 时 p95 为 252 ms。
- 关键词冷查询 p95 为 1,738 ms，超过 800 ms 目标；缓存后并发请求低于 207 ms。
- 地图冷聚合 p95 为 827 ms，略高于 800 ms；缓存后并发请求低于 164 ms。

L 档不是本轮主要验收规模，但它揭示了两个结构性限制：`INSTR` 多字段搜索无法使用普通 B-tree 完成文本命中，视口网格聚合仍需临时分组。若生产有效菜品接近或超过 50,000，且搜索词长尾导致缓存命中率低，需要启动搜索读模型重建：

1. 建立规范化搜索文档表，按菜品保存名称、别名、地区、标签和食材词元，不包含故事和私人字段。
2. 在菜品审核、编辑、标签合并事务提交后写入 outbox，由单消费者更新读模型。
3. 先使用 MySQL 可索引的词元关联表验证召回和写放大；只有规模和语义证明必要时再评估独立搜索服务。
4. 地图建立按公共数据版本和固定层级预聚合的格网表，增量维护计数；高缩放仍查原始点。
5. 双读比较总数、可见性和排序，达到一致性门槛后切换；保留旧查询开关以便回退。

该重建未在本轮实施，因为会改变数据写入链路和搜索基础设施，且 M 档已经达到约定目标。

### 5.4 资源

M 档最终快照：后端 286.7 MiB/768 MiB、MySQL 643.7 MiB/768 MiB、Redis 4.0 MiB/128 MiB、Nginx 4.7 MiB/64 MiB。运行中没有 OOM、持续连接池饱和或测试请求错误。

MySQL 已接近当前 768 MiB 容器上限的 84%。部署到合计 2 GB 服务器前应保留操作系统和文件缓存空间，不能简单把四项上限复制到同一主机后再增加其他常驻进程。

## 6. 发布前检查表

1. 记录生产当前提交、镜像摘要、数据库迁移版本、容器资源限制和自动更新机制。
2. 只读取并记录有效菜品数、地区数、图片数量与大小分布、评论/收藏/想吃数量及常用查询慢日志；不要导出私人正文到测试环境。
3. 用生产规模更新合成数据，复跑 M/L 中更接近真实规模的一档。
4. 备份数据库和上传目录，并在隔离环境实际恢复。
5. 部署兼容旧前端的新后端，执行 V21，检查表、索引、Flyway 记录和旧接口。
6. 验证登录不产生想吃或地图预热查询，抽查目录、搜索、聚合、上传和私人分页。
7. 部署前端，清除 HTML/CDN 缓存；保留带哈希静态资源，避免旧 HTML 指向已删除资源。
8. 观察首屏阶段、接口 p95、5xx、数据库 CPU/内存/慢查询、连接池等待、Redis 错误、图片派生队列和磁盘。
9. 小批人工执行图片补处理：先 dry-run，再每批 100、单并发；每批记录游标、成功、跳过和失败。
10. 真实手机至少覆盖一台低端 Android、一台常见 Android 和一台 iPhone，分别检查首次访问、已有会话、弱网、地图失败和账号切换。

## 7. 回滚

- 前端可独立回滚；旧后端接口仍保留。
- 后端执行 V21 后，不在紧急回滚中删除图片表或索引。先验证旧后端可忽略新增表和迁移记录。
- 图片原图不被覆盖或删除，派生失败可继续使用原图。
- 停止图片处理器只暂停新派生，不影响上传记录和原图访问。
- 关闭新目录/地图调用路径时切回旧兼容接口，不清理用户数据。
- Redis 缓存可直接失效并回源；不得改变会话 Redis 淘汰策略。
- 如果数据库资源升高，先停历史补图、降低并发并关闭新缓存回填，再按已验证镜像回退应用。
- 数据库恢复只用于数据损坏，并明确恢复点之后的写入会丢失。
